목적은 “지원자가 제출한 작업을 설명할 수 있는가”에 필요한 질문을 만드는 것이다.
실제 저자·성과의 진위, 지원자 신뢰도·역량·채용 합불은 판정하지 않는다.

화면, Supabase, 로그인, 답변 평가, 음성, 코딩 분야는 포함하지 않는다.

**2026-09-16: 사용자 요청으로 일시정지. 재개 지시 전에는 구현·검증·Gemini 호출을 하지 않는다.** 자동 재개나 예약 실행은 설정하지 않았다.

## 실행

```sh
npm ci
npm run check
npm test
mkdir -p output
npm run analyze -- example.pdf --track design --output output/result.json --guide-output output/questions.txt --preview-dir output/regions --events
```

루트 `.env`에 `GEMINI_API_KEY`, `GEMINI_MODEL=gemini-3.8-flash`를 설정한다.
키는 서버/CLI에서만 사용하고 출력하지 않는다. 우선순위는 CLI > 환경변수 > .env.
로더는 해당 두 키의 한 줄 값·따옴표·주석만 지원한다. 변수 치환/다중행은 지원하지 않는다.

기존 옵션을 유지한다: `--track design|marketing`, `--model`, `--skim-model`,
`--scope focused|full`, `--page-budget`, `--events`, `--output`, `--guide-output`,
`--inspect-only`, `--preview-dir`.
추가 옵션은 `--review-model`, `--budget-ledger`, `--max-cost-usd`, `--additional-budget-krw`, `--krw-per-usd`다. CLI 기본 원장은 `output/api-budget.jsonl`.
기본 모델은 `gemini-3.8-flash`. 모델 변경은 단계별 옵션으로 지정하되 검증된 가격표에 없는 모델은 호출하지 않는다.
한 번 원장에 기록된 추가 예산은 다음 실행에 옵션을 생략해도 유지되며 재시작으로 초기화되지 않는다.
**이번 20개 검증의 개발/본검증/반복 실행은 모두 별도의 동일 원장 `output/benchmark/api-budget.jsonl`을 공유한다.**
이미 있는 결과·가이드·미리보기 경로는 덮어쓰지 않으며 호출 전에 거부한다.

```ts
import {readFileSync} from 'node:fs';
import {analyzePdf} from './src/pipeline.ts';
import {Budget} from './src/gemini.ts';

const budget = new Budget('output/my-budget.jsonl', 10);
try {
  const result = await analyzePdf(readFileSync('example.pdf'), {
    track: 'marketing', model: 'gemini-3.8-flash',
    apiKey: process.env.GEMINI_API_KEY, budget,
    onEvent: event => console.log(event.type),
  });
  console.log(result.questions);
} finally {
  budget.close();
}
```

실제 호출은 PDF와 선택 영역을 Google Gemini API로 전송한다. 제출자의 사용 권한·서비스 고지·동의를 확보한 환경에서 사용해야 한다.
벤치마크 공개 원문도 재배포 권한을 뜻하지 않으며, 원문·영역 이미지·원본 응답은 Git 제외된 로컬 output에만 보관한다.

## 현재 분석 방법

```text
PDF 검사 → 전체 구조 스캔 → 필수 맥락을 묶은 페이지 선정
  → 실제 렌더링/영역 식별 → 직군별 추출 → 로컬 출처 검사 → PDF·확대 영역 대조
  → 검증된 원문/관찰로 질문 생성 → 로컬 검사 → 모델 전제 검사 → 원본 좌표로 질문 연결
```

### 1. PDF와 전체 구조

`pdf-lib`로 PDF 시그니처·구조·암호화·50 MB·1~60페이지를 검사하고 실제 PDF를 분리한다.
`pdfjs-dist`와 `@napi-rs/canvas`가 CropBox와 회전을 적용한 표시 페이지를 렌더링한다.
본문뿐 아니라 통짜 이미지, UI, 표와 그래프를 시각적으로 읽는다. 텍스트 파싱으로 비전을 대체하지 않는다.

Gemini Files API에 바이너리 업로드 → ACTIVE 확인 → URI 사용. 실행 내 동일 SHA-256 파일은 재사용한다.
12페이지 초과 문서는 8페이지 단위(경계 한 페이지 중첩) 시각 목차를 병렬로 얻고 코드가 원본 번호로 변환한다.
목차를 합쳐 모든 물리적 페이지를 정확히 한 번 분류하고 프로젝트와 후보 포인트를 찾는다.
짧은 문서는 원본을 바로 스캔하며, 긴 이미지형 페이지는 확대 타일 목차를 먼저 얻는다.
표지/소개/작업/기타, 읽기 상태, 프로젝트별 페이지와 중심·필수·선택 맥락 페이지를 받는다.
발견 프로젝트는 최대 60개, 후보 포인트는 최대 12개다. 발견 개수와 실제 집중 분석 개수는 다르다.
중심/필수/선택 번호의 무해한 중복만 제거한다. 누락·다른 프로젝트 연결은 자동으로 만들어 보완하지 않는다.
프롬프트만으로 “몇 페이지만 보라”고 하지 않고, 심층 분석에는 선택한 실제 분리 PDF를 보낸다.

### 2. 집중할 페이지 선정

기본 최대 **5페이지·3개 포인트·2개 프로젝트**. Gemini는 후보를 제안하고 최종 선택은 코드가 한다.

1. 추상적 요약뿐인 후보, 못 찾은 필수 맥락, 읽을 수 없는 필수 페이지는 보류한다.
2. 중심 + 필수 맥락 **전체 묶음**이 들어오는 후보만 고려한다. 예산에 맞춰 필수 페이지를 잘라내지 않는다.
3. 핵심 중요도(core → supporting → minor) → 미확보 확인 축 → 구체적 행동 → 다른 프로젝트 → 추가 페이지 수 → 원본 페이지 순으로 고른다.
4. 역할 / 선택 이유 / 과정·측정을 확인 축으로 삼는다. 과정과 측정은 같은 축이다.
5. 필수 묶음을 모두 선정한 뒤 남는 자리에만 선택적 배경 페이지를 넣는다.

후보가 없는 프로젝트는 첫 읽기 가능한 작업물 페이지에서 산출물 설명을 시도한다.
선정·보류 사유, 미선택 페이지, 생략한 배경을 `analysis_plan`에 남긴다.
`full`은 작업으로 분류한 모든 페이지의 심층 분석이며 표지까지 전수 검증하는 모드는 아니다.

핵심 중요도는 문제·선택 이유·변경 과정·주요 결과의 조건을 기준으로 모델이 제안한다. 약력/역할 나열이나 앞쪽이라는 이유만으로 우선하지 않는다.
모델의 중요도·프로젝트 구분이 틀릴 수 있으므로 최적 면접 품질을 보증하지 않는다.
따라서 올바른 질문 수와 핵심 포인트 누락을 별도로 보고한다.

### 3. 영역과 원문 연결

일반 페이지는 긴 변 2200px PNG, 가로세로비가 2.5를 넘으면 전체 페이지를 덮는 겹친 타일 최대 8개로 구분한다.
타일당 최대 20개 영역을 식별하고 코드가 타일 좌표를 원본 페이지 좌표로 변환한다. 동일 크롭은 실행 중 재사용한다.
화면·와이어프레임·흐름·도표·광고 소재·편집물·사진·설명문 등을 분리한다.
인접 배치만으로 캡션/전후 비교/협업 관계를 확정하지 않는다.
`source_role`은 명시 문구가 있는 경우에만 작업물/참고자료/템플릿/데이터 캡처로 지정한다.

`box=[top,left,bottom,right]`는 회전/CropBox가 적용된 표시 이미지 기준 0~1000 좌표다.
`p3:r2`처럼 원본 페이지와 영역 ID를 연결한다. 박스는 모델의 추정이며 픽셀 단위 정확도 보증이 아니다.
확대 대조는 해당 박스를 원본에서 다시 렌더링한다. 영역 긴 변 목표 1600px, 생성 캔버스 최대 4096px다.
이전의 전체 페이지 환산 4096px 제한은 제거했다. 원본 이미지 자체가 흐리면 확대해도 읽을 수 없다.
생성형 복원이나 추측 OCR로 채우지 않는다.

텍스트 레이어는 원문과 위치 확인의 보조 수단이다.
원문을 다른 위치에서 찾으면 후보를 제외하지만, 텍스트 레이어에 없다고 이미지의 문구가 없다고 판정하지 않는다.
텍스트 위치는 글꼴별 근사치이며, 비정상 문자 인코딩·이미지형 PDF에는 특히 제한적이다.

### 4. 디자인 / 마케팅 추출

공통으로 프로젝트당 8개 이내 핵심 후보를 요청한다(스키마 안전 상한 16개). 각 후보는 원문 anchor, 범주별 details, 선택 포인트 ID를 가진다.
`statement`는 해당 근거의 첫 인용/관찰에서 코드가 복사한다. 모델이 별도로 바꿔 쓴 요약을 사실로 쓰지 않는다. 원본 응답은 별도 보존한다.
원문 인용과 시각 관찰을 분리하고, 없는 값은 null이다.

| 분야 | 분리해서 추출·확인하는 내용 |
|---|---|
| 디자인 | 문제·대상·조사, 선택과 대안, 제약·수정, 검증 주장, 본인 역할, 결과물의 형태·명시 단계·사용 맥락 |
| 마케팅 | 목표·타깃·인사이트, 전략·채널·예산, 소재·실행, 실험·기여, 지표명·수치/단위·기간·분모·비교 기준·출처·귀속 방식 |

디자인은 “3가지 타입”을 “3개 타입패밀리”로 바꾸지 않는다.
작업물과 참고자료, 본인 제작과 협업자 제작, 시안과 실제 사용을 구분한다.
마케팅은 %/%p, ROAS/ROI, 목표/실적/가상, 전후 변화/인과관계를 바꾸지 않는다.
단위는 원문 `reported_value`에 그대로 보존하고, 나머지 측정 조건도 인용과 연결한다.
관례적인 CTR 분모나 실제 집행 여부를 빈칸에 추정해 넣지 않는다.

로컬 검사는 페이지·영역·포인트 ID, 연속 원문 인용, 숫자/역할/실험/사용 맥락을 보호한다.
맞지 않는 후보만 이유와 함께 제외한다. 필요한 질문 수를 맞추기 위해 근거를 보충하지 않는다.

### 5. 원본 대조와 두 가지 판정

후보를 최대 4개씩 묶어 분리 PDF + 연결 영역 확대 PNG와 대조한다.

| 필드 | 값과 의미 |
|---|---|
| source_check | supported / uncertain / unsupported: 인용·관찰·조건이 지정한 원문과 맞는가 |
| document_support | documented: 분석한 다른 자료/조건이 구체적으로 뒷받침함 |
| document_support | needs_explanation: 추가 설명 필요 |
| document_support | conflicting: 서로 다른 두 근거의 명시적 불일치 |
| document_support | not_assessed: 출처 또는 분석 범위 때문에 미판정 |

**주장이 문서에 있음과 그 주장이 입증됨은 다르다.**
주장 문구만으로 documented가 될 수 없고, 누락만으로 conflicting을 만들 수 없다.
`analysis_scope`가 분석/미분석 페이지를 구분한다. 미분석 자료를 “없음”으로 단정하지 않는다.
supported도 Gemini의 대조 결과다. 같은 모델이 반복해서 같은 오독을 할 수 있다.

### 6. 질문 생성과 검사

질문 입력은 eligible 근거의 **검증된 anchors와 미확인 필드**뿐이다.
스캔 요약·후보 설명·검토자의 해석 문장은 사실 입력으로 넘기지 않는다.
모델은 근거 ID, anchor 순번(1부터), 관점만 선택한다. 자유로운 사실 문장은 작성하지 않는다.
코드가 첫 anchor의 원문 또는 관찰을 그대로 표시하고 관점별 중립·조건부 질문을 붙인다.
관점은 문제/대상, 선택 기준, 작업 과정, 측정 조건, 담당 범위다. 역할/실험/인과관계를 새 문장으로 재서술하지 않는다.
질문은 최대 5개, 순수 담당 범위 확인은 최대 1개다. 같은 포인트/관점과 동일 근거 반복은 제외한다.

로컬 검사: 잘못된/중복 근거 ID, 동일 질문, 모델이 쓴 페이지 번호, 출처 없는 수치, 금지 판정을 제외한다.
수치는 검증된 원문 구절에만 그대로 존재한다. 모델이 단위/대상/기간을 다시 쓰게 하지 않는다.
이후 Gemini가 **실제 연결 영역 이미지**와 질문을 대조해 영역 일치, 없는 전제, 같은 답의 중복, 근거와의 관련성, 참여 확인 외 내용 여부를 각각 반환한다.
어느 필수 조건이든 실패하면 제외한다. 핵심 포인트가 빠지거나 질문이 부족하면 같은 근거 안에서 한 번만 보완 선택하고 재검사한다.
원본 생성/제외 이유를 `question_checks`에 남기며 사람이 고친 질문을 자동 결과로 집계하지 않는다.
`quality.coverage`는 선택 포인트별 질문 ID, 누락, 내용 있는 질문 수를 표시한다.
3개 이상·선택 포인트 모두 포함·참여 확인 외 최소 2개를 충족해야 `evidence_ready`, 일부만 있으면 `needs_review`다.

최종 페이지 안내와 영역은 코드가 원본 좌표에서 만든다.
자유문장에 남은 원본 문서의 숫자를 페이지 이동 라벨로 사용하지 않는다.
질문 0개는 `insufficient_evidence`이며, 이는 지원자가 아닌 분석 결과의 상태다.
자동 검사만으로 의미 정확성이 증명되지는 않으므로 실제 채용 사용 전 사람 검토가 필요하다.
[구조화 출력 공식 문서](https://ai.google.dev/gemini-api/docs/structured-output)

## 계약·안전장치·측정

진입점은 `src/pipeline.ts`의 `analyzePdf(pdfBytes, options)`.
스키마와 직군 필드는 `src/schema.ts`, 프롬프트는 `src/prompts.ts`에 있다.
기존 필드는 유지하고 `quality`, `review_model`, `source_excerpt`, `angle`, `answer_target`, 질문 검사 회차를 추가했다.
새 상태 `needs_review`, 이벤트 `page_index`가 추가되었다. `evidence_ready`의 자동 품질 조건은 강화했다.

이벤트는 `{sequence,type,elapsed_ms,data}`:
`stage → document_map → analysis_plan → page_inventory / evidence_rejected / evidence_ready → questions_ready → complete`.
실패하면 error이며 complete를 보내지 않는다. 토큰 단위 JSON 스트리밍이 아니다.
이미 검증된 부분 이벤트와 원본 응답은 실패 시에도 벤치마크 폴더에 남는다.

형식/Zod/교차 참조 위반은 같은 단계에서 1회만 재요청한다.
HTTP 오류·타임아웃·잘린 출력은 자동 재시도하지 않는다.
출력 JSON 형식 검증과 원문 의미 검증은 별개다.
API에는 지원되는 핵심 JSON Schema를 보내고 범위·개수·ID·조건은 로컬 Zod/함수에서 강제한다.

업로드 파일은 성공/오류 종료 시 이번 실행이 만든 파일만 삭제 시도한다. 정리 실패 수를 기록한다.
강제 프로세스 종료/업로드 응답 유실의 정리를 보장하지 않는다.
예산 원장은 단일 프로세스 배타 잠금을 사용한다. 잠금이나 미확정 예약을 자동 삭제해 다시 호출하지 않는다.

`metrics`는 단계별 시도/시간, 호출/업로드/재사용/정리 실패,
첫 질문 가능 근거 시간, 전체 시간, 원본 usage, 입력·출력·추론·캐시·총 토큰, 추정 비용을 포함한다.
첫 근거 시간은 TTFT가 아니다. 병렬 단계 시간 합계는 실제 경과시간보다 클 수 있다.
최대 호출 수를 고정하지 않고 실제 실패/재시도도 집계한다.

## 실제 포트폴리오 검증

출처/조건/언어/분야/페이지/해시는 `benchmark/corpus.json`, 사전 원문 기준표는 `benchmark/gold/`.
20개는 서로 다른 작성자의 native PDF이며 디자인 10개·마케팅 10개다.
기존 Notefolio 이미지 결합 PDF는 저장 결과 회귀 비교에만 사용하고 20개에서 제외한다.
출처 선정 과정의 실패는 `output/benchmark/sources/*/prepare-error.json`에 남긴다.

검수 주체는 **Codex의 별도 시각 검토**이며 사람 전문가 검수가 아니다.
모델 결과를 보기 전에 모든 페이지의 contact sheet를 보고,
텍스트 레이어를 보조로 활용하며 필요 시 원본을 확대해 프로젝트·필수 맥락·오해 방지 항목을 기록했다.
모든 작은 글자까지 판독했다는 뜻은 아니며 확대/가독성 한계는 기준표에 명시했다.

별도 결과 검수에서는 질문 본문·의도·답변 확인 항목과 연결 영역을 함께 본다.
같은 페이지에 내용이 있더라도 해당 질문의 연결 영역에 없으면 근거 연결 오류로 기록한다.
여러 화면을 설명하면서 한 화면만 박스로 연결한 경우도 영역 범위 오류다.
본인 참여가 불명확한 자료에서 역할 수행을 전제하고 참여 여부를 묻지 않으면 전제 오류로 보수적으로 센다.
같은 작업물에 같은 답을 요구하면 중복이며, 다른 작업물의 독립적 선택 이유는 별도 질문일 수 있다.
사전 핵심 포인트는 필수 맥락을 검토하고 질문이 그 핵심을 실제 다룰 때만 포함한다. 페이지를 선택했기만 하면 포함하지 않는다.
검수 의견으로 자동 질문을 고치거나 제거하지 않는다. 이 의견은 별도 `source-audit.json`에만 남긴다.

v0.6 회귀 검증 명령 예시(현재 일시정지 중이므로 재개 지시 전 실행하지 않음; 이미 결과를 본 자료이며 새 holdout이 아님):

```sh
npm run benchmark -- run --phase mvp --run UNIQUE_MVP --ids d-asad,m-hyunmin
```

다음 명령은 과거 v0.5의 동결 평가 절차다. 현재 코어로 과거 freeze를 재사용하거나 덮어쓰지 않는다:

```sh
npm run benchmark -- prepare
npm run benchmark -- run --phase dev --run UNIQUE_DEV
# 개발 3개/분야에서 수정하고 테스트한 뒤에만 고정:
npm run benchmark -- freeze
npm run benchmark -- run --phase final --run UNIQUE_FINAL
npm run benchmark -- run --phase repeat --run UNIQUE_REPEAT --ids DESIGN_ID,MARKETING_ID
# 각 결과와 원본을 별도 검토한 source-audit.json을 추가한 뒤:
npm run benchmark -- report --run UNIQUE_FINAL
```

다음은 **과거 v0.5 중단 실행**의 재개 명령이다. 현재 v0.6 코드와 과거 freeze는 다르므로 현재 MVP 재개용으로 사용하지 않는다:

```sh
# 기본은 계획만 출력하며 API를 호출하지 않는다.
node benchmark/resume.ts --from final-01 --run UNIQUE_RESUME
node benchmark/resume.ts --from final-01 --run UNIQUE_RESUME --execute
# 동결 시 미리 지정한 디자인/마케팅 1개씩, 같은 추가 비용 한도 적용:
node benchmark/resume.ts --repeat --run UNIQUE_REPEAT --execute
```

재개 코드는 frozen src/lockfile/TS 설정과 원문/기준표 해시를 확인하고 코어를 그대로 호출한다.
기존 실패·완료 디렉터리를 재사용하며 중단 시도의 비용은 run.json의 interrupted_attempts에도 남긴다.
추가 실행 코드의 해시는 orchestration_sha256에 별도로 기록한다. 고정 후 질문 품질 튜닝은 하지 않는다.

v0.5에서는 개발용 6개만 튜닝했고 나머지 14개는 고정 후 처음 평가했다. v0.6부터 기존 20개는 모두 회귀 자료이며 새 일반화 정확도를 입증하지 않는다.
코드·lockfile·TS 설정·원문 기준표·자료 목록의 해시가 고정본과 다르면 본검증을 거부한다.
질문을 수정하지 않고 원본 결과 해시와 별도 source-audit를 연결한다.
실패 문서를 성공 사례로 바꾸거나, 수정한 질문을 자동 생성 성과로 집계하지 않는다.

완료 기준: 최종 질문의 잘못된 페이지/근거·없는 수치/역할/실험 전제 0건,
분야별 최소 8/10문서에서 근거가 명확한 비중복 질문 3개 이상.
핵심 포인트 누락, 박스 오류, 제외 질문, 분석 실패와 시간·비용을 함께 보고한다.
기준 미달/미검수는 성공으로 표시하지 않는다. 20개 수치를 Gemini 일반 정확도로 해석하지 않는다.

각 실행의 `output/benchmark/runs/<run>/<id>/`에는 raw 응답, 이벤트, result.json,
questions.txt, regions, completion 또는 error, 별도 source-audit가 저장된다.
본검증 결과는 [검증 보고서](benchmark/REPORT.md)와 [기계 집계 JSON](output/benchmark/runs/final-01-resume-01/report.json), 반복/전체 비용은 [종합 JSON](output/benchmark/summary-2026-09-16.json)에 있다.
실행 실패 3개는 완성된 질문 대신 부분 원본 응답과 실패 검토를 남겼다. 완료 결과 17개와 반복 2개의 질문·영역을 별도 시각 검수했고, 자동 결과는 수정하지 않았다.

저장된 Python 결과의 페이지 선정 JSON과 TS 결과는 유료 재실행 없이 깊은 동등 비교로 확인한다.
회전(90/180/270), CropBox, 원문 위치, 암호화 표지 거부, 이미지 렌더링,
수량 대상/협업/목표/단위 왜곡, 실패·재시도·비밀키·예산·정리를 회귀 테스트한다.
실제 한국어/이미지형/작은 차트 PDF의 가독성은 원문/영역 시각 검수와 별도로 기록한다.

Python 실행 소스와 requirements는 제거했다. 기존 JSON/질문/미리보기는 보존했다.
복구용 원본은 로컬 `output/migration/python-v0.4-before-typescript.tar.gz`에 있다.
기존 수동 수정 질문 가이드는 이번 자동 생성 품질 집계에 포함하지 않는다.

## 남아 있는 한계

- 프로젝트/필수 맥락 선정 자체가 모델 판단이며 누락이 가능하다.
- 타일당 20개·최대 8타일과 입력 파일/페이지 제한이 있다. 극단적으로 긴 페이지의 작은 글씨와 원본 저해상도는 여전히 한계다.
- 코드 생성 질문은 안전한 다섯 관점으로 제한한다. 표현 다양성보다 출처 보존을 우선한 MVP이며 같은 관점도 실제 답이 다른지 추가 대조한다.
- 문자열 검사는 의미 동치/인과관계의 완전한 증명이 아니다. 모델 재검수도 동일 오독을 반복할 수 있다.
- 학생·콘텐츠 제작·영문 자료가 섞인 편의 표본이다. 경력/분야 전체로 일반화할 수 없다.
- Codex 시각 검수는 사람 전문가 합의 기준표나 저자 인터뷰를 대체하지 않는다.
